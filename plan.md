## 1. Executive Summary

**Scope.** WardSetu is a pan-India, politically neutral civic platform (ward-level issue reporting, ward representative/office operations, election-term continuity, tiered administration) built as two repositories: a NestJS + Prisma + PostgreSQL backend and a Next.js App Router frontend, communicating over a documented REST contract. Both repositories currently contain **foundation only** — no business modules, no Prisma models, no application routes beyond a placeholder page. This plan sequences the work from that foundation to a working MVP consistent with the documented schema (`docs/DATABASE_ARCHITECTURE.md`), API contract (`docs/API_SPECIFICATION.md`), and product scope (`docs/PROJECT_OVERVIEW.md`).

**Done, for the current phase.** "Done" for Phase 1 (the next phase after today's foundation) means: the location hierarchy, authentication, and the full roles/permissions resolution chain are implemented end-to-end (schema, service, guard, tests) and enforced on at least one real protected endpoint; the citizen-row backfill has run safely against a seeded dataset; and the frontend has a working auth flow, role-aware shell, and at least one screen consuming a real (non-mock) endpoint through the service-layer abstraction — proving the mock→real swap mechanism works, not just that it's designed. Everything past that (issues workflow, elections, content, tiered admin) follows the sequencing in §3.2 and §6.

### 3.2 Module build order (dependency-first)

Current state: `prisma/schema.prisma` has **zero models** (confirmed — 20 lines, config header only); `src/modules/` does not exist yet; only foundation (`config`, `database`, `common/*`, `health`) is present. Proposed order, with the dependency reasoning for each step:

1. **Location hierarchy** — `states`, `districts`, `cities`, `wards`, `localities`. Justification: almost every other table (issues, content, `user_ward_roles`, election terms) carries a scope FK into this hierarchy. Nothing else can be modeled with real foreign keys until this exists. No permission logic needed yet (all read endpoints in `docs/API_SPECIFICATION.md` §4 are public).
2. **Users & Auth** — `users`, `auth_sessions`, `otp_challenges`, and the `user_ward_roles` table itself (schema only, populated starting here). Justification: every subsequent module needs `users.id` as an actor FK (`created_by`, `actor_id`, etc.), and the citizen-row auto-create behavior (`POST /auth/otp/verify`) is the first place `user_ward_roles` gets written to. Depends only on step 1 existing as a schema target (wards don't need to be populated yet, just present, since `citizen` rows have all-NULL scope columns).
3. **Roles & Permissions catalog + `AuthorizationService`** — `roles`, `permissions`, `role_permissions` (seeded, not user-editable at this stage), `ward_role_permission_overrides`, `user_permission_overrides`, plus the guard/service described in §3.4. Justification: build this **before** any module that needs to gate a write behind a permission key, so `issues:verify`, `content:publish`, etc. are enforced from the first business endpoint, not bolted on after the fact. This is also where the `view_analytics`-cascades / `manage_*`-exact-tier distinction (`docs/DATABASE_ARCHITECTURE.md` §13.6) gets built once, generically — so it is correct for both MVP roles and the future tiered-admin roles without rework later (see §3.2 note on tiered admin below).
4. **Representatives & Elections** — `election_terms`, `representative_profiles`, `ward_representative_terms`, `representative_office_users`. Justification: depends on wards (step 1), users (step 2), and the role model (step 3) — granting `ward_rep_office` is a permission-model operation, not just a row insert. This is also where the explicit-identity-never-inferred rule (`representative_profile_id` vs `new_profile`, 409 on likely duplicate) and the election-day transaction (term close + office-user/`user_ward_roles` revocation, same transaction) are implemented — both are transactional-consistency requirements, sequenced deliberately after the transaction/audit patterns exist (step 3's service layer is the template).
5. **Issues workflow** — `issue_categories`, `issues`, `issue_media`, `issue_events`, `departments`, `issue_references`, `issue_ratings`, `issue_links`, `escalation_rules`, `issue_escalations`, `audit_logs`. Justification: this is WardSetu's core civic workflow and the first place the state machine + transactional audit pattern (§3.6) is exercised end-to-end; it depends on users, wards, and the permission model, and benefits from (but does not strictly require) the representative module existing for assignment targets.
6. **Content & Community** — `updates`, `events`, `event_rsvps`, `schemes`, `library_items`, `opportunities`, `ideas`, `idea_votes`, `polls`, `poll_options`, `poll_votes`. Justification: same dependency shape as issues (wards, users, permissions) but lower workflow complexity — no state machine, mostly CRUD + publish gating. Sequenced after issues so the permission-gated-write pattern is already proven.
7. **Team, Reports & Audit surface** — `invites`/team endpoints, the role-permission-override endpoints (`GET`/`POST`/`DELETE /wards/:id/role-permission-overrides`), `report_snapshots`, `GET /reports/*`, `GET /audit`. Justification: reporting reads across issues/content, which must already exist; the override-management endpoints are a thin API layer on top of step 3's already-built tables.
8. **Consent, devices, feature flags** — `user_consents`, `data_deletion_requests`, `device_tokens`, `notification_preferences`, `feature_flags`, `ward_feature_flags`. Justification: lowest coupling to everything else; genuinely can be built any time, scheduled last because it blocks nothing else and nothing else blocks it.
9. **Location-tiered administration** (appointment + analytics endpoints for `state_admin`/`district_admin`/`ulb_admin`) — deliberately placed **after** the MVP modules above, not interleaved with step 3. Reasoning: `docs/PROJECT_OVERVIEW.md` §16 explicitly scopes these roles as future-phase, not MVP; the underlying cascade/exact-tier logic is already built in step 3 (no rework needed), so this step is almost entirely new API surface (`docs/API_SPECIFICATION.md` §9) rather than new authorization design. Building it after the MVP modules ship means it's demand-driven, not built speculatively ahead of a real tiered-admin rollout.

This sequence matches the task's suggested ordering with one refinement: roles/permissions moves earlier (step 3, before representatives) rather than being described as a cross-cutting "middleware" layered in later, because every module from step 4 onward needs it as a hard dependency, not an add-on.

### 3.3 Prisma migration strategy

Given no production database access (§2.5) and Prisma 7.10.0 (§2.6), migrations are authored offline: edit `prisma/schema.prisma`, then `npx prisma migrate diff --from-schema <previous> --to-schema prisma/schema.prisma --script -o prisma/migrations/<timestamp>_<name>/migration.sql`, reviewed and committed, applied only by the operator (`npm run prisma:migrate:deploy`).

Sequencing the schema-level hazards named in the Ground Truth block:

1. **CHECK constraints** (`user_ward_roles`: exactly one of `ward_id`/`city_id`/`district_id`/`state_id` non-null per role). Prisma's schema DSL has no first-class CHECK-constraint syntax; author the constraint as raw SQL appended to the generated `migration.sql` in the same migration that creates the table — never as a follow-up migration, so the table is never live without it.
2. **`UNIQUE NULLS NOT DISTINCT`** (16 occurrences across `user_ward_roles`, `ward_role_permission_overrides`, `user_permission_overrides`, and others per `docs/DATABASE_ARCHITECTURE.md` §11.2). Confirm during implementation whether the installed Prisma version's schema DSL supports `NULLS NOT DISTINCT` natively in `@@unique` — if not, same approach as the CHECK constraint: hand-edit the generated SQL to add `NULLS NOT DISTINCT`, in the same migration that creates the constraint, and add a migration-file test (per `SKILL.md` §41's existing "migration framework" test category) asserting the clause is present in the committed SQL — this is the kind of drift a code review can miss but a test catches every time.
3. **Citizen-row backfill.** Sequenced exactly as `docs/DATABASE_ARCHITECTURE.md` §8.1/§17 (R16) specifies: (a) ship the `user_ward_roles` table migration; (b) ship a one-off, idempotent backfill script (`INSERT ... SELECT ... WHERE NOT EXISTS`, or `ON CONFLICT DO NOTHING` against the `NULLS NOT DISTINCT` key) as a **script the operator runs once**, not a Prisma migration (it's a data operation, not a schema change, and the operator — not this codebase — controls when it runs against production); (c) only after the operator confirms the backfill ran does application code that assumes "every user has a `user_ward_roles` row" get deployed live. Never reverse this order.
4. **Seed data for `roles`/`permissions`/`role_permissions`.** Also operator-run, idempotent, versioned alongside the schema migration that creates those tables — the nine roles and the full permission catalog are fixed by the specification (`docs/DATABASE_ARCHITECTURE.md` §13.4–13.5), not runtime-configurable at this stage (per §16.9, dynamic custom roles are explicitly "not built, revisit later").

### 3.4 RBAC implementation approach

**Proposal: a dedicated `AuthorizationService`, invoked by a `PermissionsGuard`.**

- A `PermissionsGuard` (NestJS `CanActivate`) reads a `@RequirePermission('issues:verify')`-style decorator on the route handler, extracts the request-scoped resource (ward/city/district/state ID from route params or the loaded resource), and calls `AuthorizationService.can(userId, permissionKey, scope)`.
- `AuthorizationService` is a plain injectable service, not baked into the guard, because permission resolution requires database reads (the user's `user_ward_roles` rows, the ancestor-chain walk for cascading `view_analytics`-shaped permissions, the three-tier override precedence) that are easier to unit-test and reason about as a service than as guard logic. The guard's only job is the NestJS-lifecycle wiring (run before the handler, throw `ForbiddenException` on denial); all authorization _logic_ lives in one service, so "never hardcode role capabilities in application code" (`CLAUDE.md`) has exactly one place to be true.
- Resolution order inside the service matches `docs/API_SPECIFICATION.md` §11.2 exactly: identify role(s) via `user_ward_roles` (respecting `election_term_id` currency and walking the ancestor chain for cascading permissions) → platform default (`role_permissions`) → `ward_role_permission_overrides` → `user_permission_overrides` (ward-specific, then global) → allow/deny.
- **Why a guard and not an interceptor:** guards run before the handler and are NestJS's designed extension point for "should this request even proceed" — denying inside an interceptor means the handler's side effects (including any DB writes) may already be in flight. Authorization must be a pre-condition, not a response-shaping step.
- `GET /users/:id/permissions` (already in `docs/API_SPECIFICATION.md` §6) should call the exact same `AuthorizationService` resolution path used by the guard — never a second, parallel implementation "for display purposes." That endpoint is also what the frontend is instructed to drive its capability-aware UI from (`docs/ARCHITECTURE.md` §14 both repos) — if the two implementations ever diverge, the frontend UI and the backend's actual enforcement would silently disagree.

### 3.6 Testing strategy and coverage expectations

Layers, per `docs/ARCHITECTURE.md` §18 (this plan sequences it, doesn't redefine it): unit (services/utilities in isolation), service/application (business rules without HTTP), controller/API (request/response contract), integration (cross-module effects, e.g. an issue transition producing both an `issue_events` row and an `audit_logs` row), and database-related (migration structure, no live DB required — already an established category per `SKILL.md` §41).

Two tests this plan calls out explicitly, because they test properties the schema's own gap log leaves open (§2.6/§7) rather than obvious happy paths:

1. **Stale `election_term_id` rejection.** Construct a `user_ward_roles` row for `ward_representative`/`ward_rep_office` whose `election_term_id` points to a term where `ward_representative_terms.is_current = false` (i.e., a closed term whose revocation transaction has not yet run, or a data state that should never persist but must not be trusted if it does). Assert `AuthorizationService`/`PermissionsGuard` denies access. This exercises the "respecting `election_term_id` currency" clause in `docs/API_SPECIFICATION.md` §11.2 directly, and is exactly the kind of check the still-open "mechanical detail of the hierarchy walk" gap (`docs/DATABASE_ARCHITECTURE.md` §17.2 item 2) makes worth locking down with a test rather than an assumption.
2. **Citizen-row backfill idempotency.** Run the backfill script twice against the same seeded dataset (some users with an existing `citizen` row, some without). Assert: every user has exactly one `citizen` row afterward, no duplicate-key/constraint errors on the second run, and no existing non-citizen role rows were touched. This directly tests the "safe to run more than once" requirement in `docs/DATABASE_ARCHITECTURE.md` §8.1.

### 3.7 Security checklist specific to this schema

- Every privileged write (role grant/revoke, permission override, election-term open/close, office-user grant/revoke, issue state transition, escalation-rule change) writes an `audit_logs` row in the **same transaction** as the write itself — not best-effort, not fire-and-forget.
- Session/role revocation on term close: the outgoing `representative_office_users` grants and their `user_ward_roles` rows are revoked in the same transaction that sets `ward_representative_terms.is_current = false` — never as a separate, later cleanup job.
- The `escalation_rules:manage` (ward-scoped) / `escalation_rules:manage_platform_defaults` (platform-only, `ward_id IS NULL` rows) split is enforced at the `AuthorizationService` level, not by convention — a ward admin's token must never be able to reach the platform-default row through the ward-scoped endpoint.
- No permission check is ever resolved client-side, ever, including for "just showing a menu item" — the frontend's `GET /users/:id/permissions` call (§3.4) is the only source of truth the UI is allowed to branch on, and even that is UX-only per `docs/ARCHITECTURE.md` §14.
- New-term identity is always explicit (`representative_profile_id` or `new_profile`, 409 on likely duplicate) — never inferred by name/mobile match, enforced in the service layer, not left to the caller's good behavior.
- `NULLS NOT DISTINCT` constraints (§3.3) are a security-relevant integrity control, not just a data-quality nicety — without them, a user could accumulate duplicate override rows with different `effect` values and get a resolution-order race. Treat any migration touching these tables that doesn't preserve the clause as a blocking review finding.

Confirmed via `package.json` and filesystem, not assumed: `next@16.3.6`, `react@19.3.0` / `react-dom@19.3.0`, `radix-ui@1.6.7`, `typescript@6.0.3` (+ `typescript7` for `npm run typecheck`), Node/npm engines `24.21.0`/`11.19.0` — matching `CLAUDE.md`/`SKILL.md` exactly.

**Actual current state: project setup only**, confirmed on disk: `app/` contains only `page.tsx`, `page.module.css`, `layout.tsx`, `icon.svg` (the placeholder page). `styles/theme/` is fully populated (`tokens.css`, `semantic.css`, `typography.css`, `spacing.css`, `radii.css`, `shadows.css`, `motion.css`, `themes.css`, `components.css`) — the token architecture from `docs/DESIGN_SYSTEM.md` is already in place. **No `components/`, `features/`, or `services/` directories exist yet.** This matches `SKILL.md`'s own "Current state: project setup only" note (§63/119) — not a surprise, but confirmed rather than assumed.

### 4.2 Project structure / folder conventions

Follow `docs/ARCHITECTURE.md` §7–§9 and `SKILL.md` §17 exactly (this plan does not redefine the structure, only sequences populating it): `app/` route groups (`(public)`, `(auth)`, `(admin)`, `(ward)`, `(citizen)`) created as their first real route lands, not scaffolded empty in advance (per `SKILL.md` §17: "do not create folders merely for the sake of folders"); `components/{ui,radix,navigation,layout,forms,tables,charts,feedback,data-display}` for domain-agnostic shared components; `features/<domain>` for domain-specific composition; `services/{contracts,mock,api}` for the API-integration layer (§4.5 below); `i18n/`, `contexts/`, `hooks/`, `lib/` as cross-cutting infrastructure.

### 4.3 Design system implementation approach

Per `docs/DESIGN_SYSTEM.md` §1–§4 and `docs/ARCHITECTURE.md` §9–§10 (not restated here): Radix primitives supply accessible interaction behavior; WardSetu's own CSS Modules + the `styles/theme/` custom-property layers supply all visual styling — Radix's own default styling is never used. Concretely, each shared component in `components/radix/` wraps one Radix primitive once (e.g. a single `Dialog` wrapper used everywhere a dialog is needed), applies WardSetu classes/tokens via `className`/`data-state`/`asChild`, and that wrapper — not the raw Radix import — is what `features/*` code uses. This keeps the "don't let third-party defaults dictate the visual language" rule (`SKILL.md` §27) enforceable in one place instead of at every call site.

### 4.4 State management patterns — a concrete rule, not "it depends"

Following the classification already established in `docs/ARCHITECTURE.md` §11:

| State category                                                 | Mechanism                                                                                         | Rule                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server/Data state (anything from an API)                       | The service layer (§4.5) + a custom hook, never global state                                      | If it came from `GET`/`POST` to the backend, it is fetched through a hook wrapping a service call. It is never copied into a Context "for convenience," because the service layer is already the single source of truth and a second copy can go stale. |
| UI state (sidebar collapsed, active tab, dialog open)          | Local `useState`/`useReducer`, or a scoped Context only if genuinely shared across a subtree      | Default to local state. Promote to Context only when at least two components more than one level apart need the same value — not preemptively.                                                                                                          |
| Form state                                                     | Local to the form component/hook                                                                  | Never global. Validation is client-side-for-UX only (§4.6/§4.7 backend note); the backend revalidates independently.                                                                                                                                    |
| Session/Auth state                                             | One dedicated `AuthContext`, backed by the mechanism the backend's session architecture specifies | This is the one deliberate exception to "no global state for convenience" — auth identity is genuinely needed everywhere, so it is the one sanctioned app-wide Context.                                                                                 |
| URL state (filters, pagination cursor, selected tab via route) | Search params / route segments                                                                    | Never duplicated into `useState` — read from and write to the URL directly, so back/forward and shareable links work for free.                                                                                                                          |
| Local component state                                          | `useState`/`useReducer`                                                                           | The default for anything not listed above.                                                                                                                                                                                                              |

No state-management library (Redux, Zustand, etc.) is introduced at this phase — `SKILL.md` §35 explicitly allows revisiting this "if complexity genuinely requires it," which has not yet been demonstrated with zero business modules built.

### 4.5 Route/surface structure mapped to the nine roles

| Surface                                                                     | Roles it serves                                                      | Genuinely distinct UI, or same view + permission-gated actions?                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public site (`(public)`)                                                    | Unauthenticated / citizen (pre-login)                                | Distinct — no auth, SEO-optimized, no dashboard chrome.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Citizen app (`(citizen)`)                                                   | `citizen`                                                            | Distinct — mobile-first, its own navigation and information architecture; not a permission-gated view of anything else.                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Ward dashboard (`(ward)`)                                                   | `ward_staff`, `ward_representative`, `ward_rep_office`, `ward_admin` | **Same views, permission-gated actions and navigation**, not four separate UIs. All four roles operate on the same ward-scoped data (issues, content, team); what differs is which actions are visible/enabled (`ward_rep_office` never sees team-management or election-recording controls; `ward_staff` has a narrower nav than `ward_admin`/`ward_representative`). Building four parallel dashboards would duplicate nearly everything and drift out of sync with the permission model in `docs/DATABASE_ARCHITECTURE.md` §13.5.6/§4.4 the moment one of them is updated and the others aren't. |
| Tiered-admin consoles (future phase, per §16 of `docs/PROJECT_OVERVIEW.md`) | `ulb_admin`, `district_admin`, `state_admin`                         | Distinct from the ward dashboard (different scope, cascading analytics views), but **shared among themselves** — one console shell whose scope (city/district/state) and available `manage_*` actions come from the caller's actual role, not three separate builds.                                                                                                                                                                                                                                                                                                                                |
| Platform admin                                                              | `platform_admin`                                                     | Distinct — the only role with unconditional access to every permission, including cross-tenant/global configuration (role/permission catalog editing, platform-wide escalation defaults, platform-wide feature flags).                                                                                                                                                                                                                                                                                                                                                                              |

The load-bearing rule from this table: **one ward-dashboard codebase, not four**; role differences are expressed as permission-gated UI, driven by `GET /users/:id/permissions` (§4.6), not as separate route trees per role.

### 4.6 Mock-to-real API migration plan

Per `docs/ARCHITECTURE.md` §12 (restated here only as the concrete mechanism, not redefined): every feature calls a hook (`useIssues()`), which calls a service interface (`issueService`), which is bound at composition time to either `MockIssueService` (in `services/mock/`) or `ApiIssueService` (in `services/api/`), both implementing the same contract type defined in `services/contracts/`. The swap point is a single binding location (e.g. one factory/provider that decides mock vs. real based on environment configuration), not a per-component import change — so migrating a domain from mock to real is a one-line change in that binding, with zero component or hook edits, provided the mock's contract was accurate. This is why the contract is written and reviewed **before** the mock implementation, not derived from whatever the mock happens to return.

### 4.7 i18n implementation approach (en/hi)

Per `docs/ARCHITECTURE.md` §19 (English and Hindi initially, Devanagari font already in the token layer per `docs/DESIGN_SYSTEM.md` §7): translated strings live in a dedicated `i18n/` directory, keyed by a stable string ID (never by the English text itself, to avoid churn when copy changes), loaded per-locale. Locale is part of session/tenant context (§4.4's `AuthContext`-adjacent state, or a route-level locale segment for public pages — a deliberate rendering-strategy decision per `docs/ARCHITECTURE.md` §5/§19, not an accident). No UI copy is hard-coded inline once a feature has more than a placeholder string.

### 4.8 Accessibility checklist

Per `docs/DESIGN_SYSTEM.md` and `docs/ARCHITECTURE.md` §20 (WCAG 2.2 AA target, not redefined here): keyboard navigation and visible focus on every interactive element; correct ARIA/semantics for dialogs, menus, tabs, and forms (Radix primitives supply this by default — do not override it away with custom event handling that breaks it); sufficient contrast (the specific token-level contrast fixes already recorded in `docs/DESIGN_SYSTEM.md` §3 — `--ws-warning-dark` for warning text, `slate-600` for muted text, `--ws-gold-dark` for gold text — must be used as-is, not re-derived per component); `prefers-reduced-motion` respected for all motion; adequate touch targets on mobile (`docs/DESIGN_SYSTEM.md` §17). Verified with automated tooling (axe, already wired per `README.md`) and manual keyboard/screen-reader passes before a surface is considered done — automated tooling alone is not sufficient sign-off.

### 4.9 Testing strategy

Per `docs/ARCHITECTURE.md` §24 (not redefined): Jest + React Testing Library for unit/component tests, Playwright + `@axe-core/playwright` for e2e/accessibility, prioritized per `SKILL.md` §92 (design-system components → navigation → auth UI → role-based navigation → forms → tables → error states → responsive layouts → citizen flows → admin flows). `tests/theme-guard.test.ts` (already present) is a standing architectural test, not a feature test — it must stay green through every phase, since it is what makes §4.3's "one visual system" claim enforceable rather than aspirational.

## 5. Integration & Environment Plan

- **Local dev parity with production:** run the exact pinned versions locally — Node 24.21.0/npm 11.19.0 via `nvm` (per both `README.md`s), a local PostgreSQL matching 16.15 (a separate local database, e.g. `wardsetu_dev`, never the production connection string per `CLAUDE.md`/`SKILL.md` §16), and the same ports in spirit even though local dev binds differently (`npm run start:dev` on `127.0.0.1:2010` for backend, `npm run dev` on Next.js's default port for frontend — production-port binding, `127.0.0.1:2020`/`127.0.0.1:2010`, is verified only by the production `start`/`start:prod` scripts, per `SKILL.md` §120/backend §7).
- **CI recommendation:** run the existing validation sequences (`npm run prisma:validate && npm run typecheck && npm run lint && npm run format:check && npm run build && npm test` for backend; `npm run typecheck && npm run lint && npm run format:check && npm test && npm run build && npm run test:e2e` for frontend) on every PR, matched to what `SKILL.md`/`README.md` already define as the manual validation sequence — CI should run the same commands a developer runs locally, not a separate parallel check list that can drift from them.
- **Deployment sequencing:** backend migrations are generated in this repo and applied only by the authorized operator (`npm run prisma:migrate:deploy`), never automatically from CI, per the explicit database-access boundary (§2.5). Deploy order per release: (1) operator applies any pending migration + runs any one-off data script (e.g. the citizen-row backfill, once, per §3.3), confirms success; (2) backend application code that depends on that migration deploys; (3) frontend deploys against the now-live backend contract. Never deploy frontend code that assumes an endpoint the backend release hasn't confirmed live.

## 6. Milestones & Phasing

- **Phase 0 — Foundation (already shipped).** Backend: config validation, Prisma-backed `DatabaseModule`, JWT infra (no login endpoints yet), health/readiness, global exception filter + response envelope (see §3.5 for the envelope caveat), ESLint 9 flat config, Jest unit + e2e harness. Frontend: Next.js App Router scaffold, security headers (`next.config.ts`, `proxy.ts`), the full `styles/theme/` token layer, placeholder page, test/lint/format tooling. **Exit criteria:** both repos build, lint, typecheck, and test clean on the pinned toolchain (confirmed true today).
- **Phase 1 — Identity & Authorization.** Backend: location hierarchy schema, users/auth (OTP login, citizen-row auto-create), roles/permissions schema + `AuthorizationService` + `PermissionsGuard`, the citizen-row backfill script (tested per §3.6), envelope/pagination decision resolved (§3.5). Frontend: auth flow UI (login/OTP), `AuthContext`, the role-aware app shell (nav that reflects `GET /users/:id/permissions`, not a hardcoded role map), the mock→real service-layer swap proven on at least one real endpoint. **Entry criteria:** Phase 0 done. **Exit criteria:** a real user can OTP-login, get a `citizen` row, and the frontend correctly gates at least one UI affordance off a real permission check round-tripped through the backend.
- **Phase 2 — Representatives & Elections.** Backend: `election_terms`/`representative_profiles`/`ward_representative_terms`/`representative_office_users`, the explicit-identity new-term workflow, the election-day transaction (term close + revocation). Frontend: ward dashboard shell (§4.5), representative/office-user management screens gated correctly for `ward_representative` vs. `ward_rep_office`. **Exit criteria:** a full election-term cycle (open term → grant office user → close term → office user access revoked, ward data untouched) is demonstrable end-to-end with tests.
- **Phase 3 — Issues Workflow.** Backend: full issue state machine + transactional audit trail, escalation rules (ward-scoped and platform-default, split enforced). Frontend: issue reporting (citizen), issue management (ward dashboard). **Exit criteria:** a citizen-reported issue can move through every documented state transition with a correct `issue_events`+`audit_logs` pair at each step, and escalation-rule scoping is enforced (tested per §3.7).
- **Phase 4 — Content & Community.** Backend + frontend for updates/events/schemes/library/opportunities/ideas/polls, publish-permission gating (`content:publish` opt-in via ward override, per the corrected v6.0 worked example). **Exit criteria:** each content type supports its documented CRUD + publish flow with the same permission model as Phase 1–3, no bespoke authorization path introduced.
- **Phase 5 — Team, Reports, Consent/Devices/Feature Flags.** Lowest-coupling remaining MVP surface. **Exit criteria:** team invite flow, reporting/export, audit log viewer, consent/deletion-request flow, device registration, and ward-scoped feature flags all live.
- **Phase 6 — Location-Tiered Administration (future phase, not MVP).** State/district/ULB admin appointment + cascading analytics endpoints and consoles, built on the already-generic `AuthorizationService` from Phase 1. **Entry criteria:** explicit product decision to activate these roles (per `docs/PROJECT_OVERVIEW.md` §16, this is deliberately not part of the minimum rollout) — do not start this phase speculatively ahead of that decision.
